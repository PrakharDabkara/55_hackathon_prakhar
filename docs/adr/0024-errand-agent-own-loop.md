# 0024. Errand agent: own loop, terminal tools, server-side truth

Status: Accepted · 2026-10-16 (Day 12: plans from learned stock only; Day 13 amendment below: pinging, waiting, asking the user)

## Context

The errand agent takes a task ("school project ke liye chart paper, fevicol aur sketch pens"), finds each item and returns a plan with a route (brief, Errand flow). It calls tools, so a successful prompt injection is no longer a wrong catalog item (ADR-0021) but a wrong plan shown as fact. The brief fixes the shape: our own loop, no agent framework, durable state in Postgres, the same tool definitions as the MCP server (ADR-0023).

## Decision

1. **Our own loop on the provider port.** `LlmProvider.chatWithTools({system, messages, tools, maxOutputTokens, purpose, forceTool?})` returns `{toolCalls[], text, usage, model, latencyMs}`. The Gemini adapter uses native function calling with declarations generated from the tools' zod schemas (`parametersJsonSchema`), sends the thought signature Gemini attaches to a call back untouched, and merges neighbouring user turns. The fake adapter plays scripted turns (`playChat`, `onChat`). `createAiClient.chatWithTools` adds the timeout (30 s), retries, the breaker and one `ai_calls` row per call, purpose `errand`. No framework: the loop is about 150 lines in `modules/errands/agent.ts` and every step is ours to log and cap.
2. **Tools run in process, as the errand's user.** `resolve_item`, `find_item_nearby` and `plan_route` come from the shared registry (inputs reused with `.omit()`, so limits cannot drift), plus one agent-only terminal tool, `submit_plan`. The user's location is injected by the server: the agent variants take no coordinates, the results leave out shop coordinates, and the descriptions say "near the user". `plan_route` takes shop ids and the server looks the coordinates up. `ask_shops` is not offered today (Day 13), and a call to it is an error result that pings nobody. A bad call, an unknown tool or a failing tool becomes an error the model can read; the errand carries on.
3. **Server-side truth on `submit_plan`.** The model proposes, the server decides. An item is `likely` only if the item exists, the shop exists and the shop has unexpired learned stock of that exact item within 5 km of the errand. Anything else becomes `not_found` and records why (`unknown_item`, `unknown_shop`, `no_shop`, `no_fresh_stock`). Prices, shop names and distances come from the database; the `pricePaise` the model sends is ignored. Then the server runs the route planner over the surviving shops (at most 8; the rest become `too_many_shops`) and stores `orderedStops`, `legsM`, `totalM`, `totalPricePaise` and `savingsPaise` against the catalog reference price (signed: negative means dearer than reference; unknown prices count as zero). The agent therefore never claims stock that no learned stock backs; "confirmed" appears only on Day 13.
4. **State in Postgres, a job to run it** (migration 010). `errands` holds the task, location, state, `version`, counters, plan and `failure_reason`; `errand_steps` holds one row per model call and tool call (arguments, a small result digest, tokens, latency). `state` is text with a named CHECK, not an enum: Day 13 adds `NEEDS_INPUT` and `WAITING_FOR_SHOPS` by dropping and re-adding the constraint, a quick metadata change (`ALTER TYPE ... ADD VALUE` is the awkward one). Transitions are one `UPDATE ... WHERE state = $from`, as for requests; a pure state machine says what is allowed. The BullMQ queue `errand` runs with concurrency 1 (the free tier allows 15 model calls a minute; with Gemini a call is also paced 4 s apart), job id `errand-<id>`, one attempt (failure is a state in Postgres, not a retry behind its back).
5. **One run at a time, by a lease.** A run claims the errand with one UPDATE that needs `state = PLANNING` and no live `lease_until`; it renews the lease each step and stops if it lost it. A second run gets `busy`, a finished errand `skipped`. A run that died leaves a lease that runs out; the next run clears the half-written log and starts over (Day 13 will resume from the log instead).
6. **Guardrails are configuration, not prompt text.** `ERRAND_MAX_ITEMS` 10, `ERRAND_MAX_STEPS` 8 model calls, `ERRAND_TOKEN_BUDGET` 20,000 (input plus output of the errand's own model calls), `ERRAND_USER_HOURLY_LIMIT` 5, `ERRAND_TASK_MAX_CHARS` 500. When a cap is about to be crossed (the last allowed call, or the budget spent) the model is told "budget reached — submit your best plan now" and may call only `submit_plan` (`forceTool`). If it still does not, the errand is `FAILED` with `failure_reason` `step_limit` or `token_budget` and a partial plan: what `find_item_nearby` had found. Other reasons: `ai_unavailable` (after retries; 3 on Gemini, 1 elsewhere), `queue_unavailable`, `internal_error`. The hourly limit counts rows under an advisory lock, so two requests cannot both slip through.
7. **The task is data.** It is cut to one line, stripped of control characters and of the `<<<` `>>>` marks, and sent only inside `<<<TASK ... TASK>>>`; the system prompt says it is data. A task that matches the instruction patterns of ADR-0021 (`looksLikeInstruction`) is refused at `POST /errands` with `422 task_rejected` and a plain message: nothing is stored, queued or sent to a model, and the log line carries no task text. That costs a false positive some friction, which is cheaper than an agent that sees the text. The hard guard is point 3: whatever the model was talked into, only database-backed claims survive.
8. **API.** `POST /errands {task, lat, lng, budgetPaise?}` (seeker) answers `201 {id, state}`; `GET /errands/:id` (owner only, 404 otherwise) returns state, `progress` (Hinglish lines built from the step log on read: "Samjha: 4 cheezein", "Chini: 7 dukaanon mein mili"), plan, `failureReason` and usage. If the queue is down the errand is `FAILED` (`queue_unavailable`) at once.

## Privacy: an amendment to ADR-0020

ADR-0020 allows only query text and catalog names to reach the free tier. The errand agent needs to choose between shops, so its prompts also carry, from tool results, **public business data**: shop id, shop name, distance in metres, learned price and freshness. They never carry the user's id, phone, coordinates or any shop coordinates; the task text and optional budget are the customer's own words. A test records every prompt and asserts none of those appear. **Never in a prompt or tool result: shop phone numbers, owner user ids, any user id or user data.** A test gives a shop a phone and an owner and asserts that no phone-number pattern (`+91…` or ten digits) and no id of any user in the database appears in anything sent to the model. Approved on 2026-10-16 on that condition. With real shopkeepers, move to a paid tier whose terms exclude training on prompts.

## Amendment 2026-10-16: timeouts per purpose, a fallback model, failure kinds

The first live errands failed with `ai_unavailable` at step 0 and a log line with no reason. The cause was the 8 s limit chosen for small resolve calls (ADR-0020) applied to errand calls, which carry tool schemas and take 2 to 20 s, and a free tier that answers 503 "high demand" slowly (a 503 took up to 12 s to arrive). Three changes, all in `createAiClient`:

- **Time limit per purpose.** Resolve and embed calls keep 8 s. Errand calls get `ERRAND_AI_TIMEOUT_MS` (default 30,000). A timeout is now retried like a 429 or 5xx.
- **Fallback model** `GEMINI_FALLBACK_MODEL` (blank: none). After a timeout, 429 or 503 from the primary, the next attempt of that call (and the rest of it) runs on the fallback; the next call starts on the primary again. The log says which model answered (`fallback: true`) and `ai_calls.model` holds it. Other errors (500, 4xx) behave as before. Chosen on 2026-10-16 from `npm run ai:models` by trying candidates with the real errand prompt and tools, then eight calls in a row each: `gemini-3.5-flash-lite` answered 8 of 8 (2 to 14 s, about 6 s on average, no hidden thinking tokens, a stable name, and a different model from the primary, which answered 503 after three calls in the same test). Rejected: `gemini-3.5-flash` (fastest, 2 to 4 s, but 429 within a few calls: a very small free quota), `gemini-3.6-flash` (429 on every call), `gemini-3.1-flash-lite-preview` (same family as the primary, 503 after six calls, and previews get withdrawn), `gemini-flash-lite-latest` (works, 4 to 7 s, but an alias that can change under us) and `gemini-2.5-flash-lite` (404 for this key). The fallback is slower than a healthy primary, so it needs the 30 s errand limit; its job is to turn the primary's bad minutes into a slower answer instead of a failed errand. Thinking models (such as `gemini-3.5-flash`) spend hidden tokens against `maxOutputTokens`, so a cap below about 300 can end with no answer.
- **Failures say why.** Each failed attempt logs `purpose, model, attempt, kind, status, code, latencyMs, message`; `kind` is `timeout`, `http`, `network`, `invalid_output`, `breaker` or `other`, the same word stored in `ai_calls.outcome` (migration 011; the old `error` and `skipped_breaker` became `other` and `breaker`). The message is cut to 160 characters, has key-like strings removed, and for HTTP errors is only Google's own short reason for a 429 or 5xx, never anything that could echo a prompt. Breakers are now per purpose (`resolve_query`, `embed_query`, `embed_catalog`, `errand`), so one failing feature cannot switch off another.
- **Health check** `GET /admin/ai/ping` (admin only): one tiny `generateJson` and one tiny `chatWithTools` call with the primary and the fallback model, straight to the provider with the same limits, writing nothing and skipping the breakers. It answers `{ok, results: [{call, model, ok, kind, status, latencyMs}]}`.

## Amendment 2026-10-16 (Day 13): patience — ask shops, wait, resume, ask the user

The agent can now ping shops and stop while they answer. No model call is ever held open while waiting.

- **Tools.** `ask_shops {itemId, targetPricePaise?}` opens a normal request (the same path as a seeker search, location injected, idempotency key `errand-<id>-<itemId>`) and links it in `errand_requests` (one per item; cap `ERRAND_MAX_ASK_SHOPS` 6; asking again about an item is free). `get_request_status {requestId}` works only for linked requests and returns shop id, name, distance, price, freshness, source: no coordinates, phones or user ids (the privacy test now covers it). `ask_user {question, options?}` ends the run (cap `ERRAND_MAX_QUESTIONS` 2; over the cap it is an error result and the agent carries on). Calls after `ask_user` in the same turn are not run but still get an error response, so every function call has its response.
- **States** (`state` stays text with a CHECK, migration 012): `WAITING_FOR_SHOPS`, `NEEDS_INPUT`, `EXPIRED`, `CANCELLED` beside the old three. Events: `ASKED_SHOPS`, `ASKED_USER`, `SHOPS_REPLIED`, `USER_ANSWERED`, `EXPIRE`, `CANCEL`. Every move is one `UPDATE ... WHERE state = $from` (or, for the two wake-ups, with the due condition inside the WHERE), bumps `version`, and sends the owner an `errand.updated` hint. Test: every state × event.
- **When a run ends in WAITING.** A turn whose calls are all `ask_shops` (at least one opened or found a request) ends the run at once: no third model call. A text-only turn from an errand that has linked requests also means "I am waiting". The wait deadline is the shorter of `ERRAND_RESUME_AFTER_MS` (45 s) and what is left of `ERRAND_MAX_WAIT_MS` (5 min, summed over all waits in `waited_ms`). If every request is already out of PINGING (enough learned stock, or a shop answered while we moved) it wakes immediately.
- **When it wakes.** One guarded UPDATE (`resumeWaiting`): state is WAITING and (the deadline passed, or no linked request is still PINGING and unexpired). A request with a yes is ANSWERED, so "or has a yes" is the same test. Three callers use it: the job (a delayed BullMQ job `errand-<id>-w<version>` for the timer), the waker (the existing post-commit `request.updated` publish, via `realtime.onPublish`; a short timer, `ERRAND_RESUME_DEBOUNCE_MS` 1 s, makes a burst of answers across requests one check) and the sweeper. Because the UPDATE is the gate, six racing resumes make exactly one; the run itself still needs the lease. A first YES to a request answers it and closes its other pings, so a "burst" is across requests, not across shops.
- **Jobs are nudges.** `runErrand` on a WAITING or NEEDS_INPUT errand whose time has not come returns `skipped`. Job ids carry a key (`-w3`, `-r4`, `-s...`) so a later wake-up is never swallowed by a retained completed job.
- **Max wait.** When a run starts with `waited_ms >= ERRAND_MAX_WAIT_MS` the model is told to submit now and may call only `submit_plan` (`forceTool`); if it does not, FAILED `wait_limit`.
- **Questions.** `POST /errands/:id/answer {text | optionIndex}` (owner only; 409 unless NEEDS_INPUT; 400 unless exactly one; text at most 200 characters; an answer that reads like an instruction is refused like a task). The answer reaches the model only between `<<<ANSWER` marks. No answer within `ERRAND_ANSWER_TIMEOUT_MS` (10 min) resumes with "user did not answer — skip that item and note it".
- **Durable conversation.** `errand_steps.payload` holds each message exactly as the model saw or wrote it: model turns with function calls (id, name, args, thought signature), tool results in full, and `note` rows for every server-added user message (resume notes, answers, nudges). A run rebuilds the conversation from the log (`conversation.ts`), so a resumed turn is valid for Gemini: calls and signatures in order, every call followed by its response. A model turn whose tools never ran (a worker died) gets "interrupted" responses; the side effect is not repeated blindly (and `ask_shops` is idempotent by key anyway). On resume the agent is shown the fresh status of every linked request in a note. The old "clear the half-written log and start over" is gone: a lease that expires now means "carry on from the log".
- **Sweeper** (inside the existing 60 s expiry sweep, `sweepErrands`): expire overdue errands; resume WAITING ones that are due (also catches a missed event); resume NEEDS_INPUT past its answer deadline; re-queue PLANNING errands whose lease ran out, or with no lease and quiet for 90 s. This is the Redis-loss repair: Postgres holds every deadline.
- **Expiry and cancel.** `ERRAND_EXPIRY_MS` (15 min) from creation: the sweeper, a run (at each step), and a read (lazy) move the errand to EXPIRED with whatever it has (the found-so-far digest, or its plan), and close its open requests. `POST /errands/:id/cancel` does the same with CANCELLED; the lease check ends a run in progress. A finished errand also closes its linked requests. Late shop answers still teach inventory (ADR-0016).
- **Server-side truth, extended.** `confirmed` only if a YES ping exists for that shop and item in this errand's linked requests; the price is that ping's, the freshness "Confirmed 2 min ago". Else `likely` if the shop has fresh learned stock (downgrade `not_confirmed` when the model said confirmed). Else `not_found`. The model's word never decides; a YES to a request outside the errand does not count.
- **Progress** is still built on read from the log, now with facts from the database: pings sent per request ("6 dukaanon se pooch raha hoon: phenyl"), each yes ("Mishra Kirana ne haan kaha ₹42"), "Jawab ka intezaar…", "Aapse ek sawaal: …". Admin stats: `GET /admin/errands/stats?hours=24`.
- **Rejected:** a `wait_for_shops` tool (one more thing to get wrong; the shape of the turn says it); resuming by a timer inside the process (lost on restart); synthetic function-call parts to show statuses (Gemini wants signatures on its own calls; a plain note is safe); waking from the answer path in a second table-based queue (the publish after commit already exists).
- **Limits of this design.** The waker is in-process: with several API instances an answer handled elsewhere is caught by the 45 s timer or the sweeper, not instantly. The default `ERRAND_MAX_STEPS` of 8 model calls is tight for an errand that asks, waits and asks the user; raise it after reading step logs.

## Alternatives rejected

- **An agent framework (LangGraph, the Claude Agent SDK):** hides the loop we must cap, log and resume; the brief says no.
- **Letting the model's plan stand and checking afterwards:** then "likely" would be a claim. Checking is the point of the terminal tool.
- **Giving the model coordinates (or a lat/lng on each tool):** one more thing an injected task could aim; the server already knows where the user is.
- **A Postgres enum for state:** a Day 13 migration that cannot run in the same transaction as its use.
- **Advisory locks held for a whole run:** pins a pool connection for minutes. The lease is a row.
- **Rejecting nothing and only wrapping the task:** it works (the server check is the hard guard) but a model that obeyed the text would still burn the budget; refusing the obvious cases is free.
- **Retrying the whole job on failure:** hides the cost and the reason; FAILED with a reason is visible.

## Consequences

- Day 13 added states, `ask_shops`, a resume from `errand_steps` with thought signatures, and `confirmed` status (amendment above).
- The free tier answers 503 "high demand" a good share of the time; the smoke runs needed retries, and `ai_unavailable` is a normal outcome, shown as such.
- Straight-line route distances, as for `plan_route` (ADR-0023).
- `resolve_item` inside the agent uses the normal resolution pipeline, so it may add its own `resolve_query` calls to `ai_calls`; they are not counted in the errand's token budget.
- The fallback model has its own free quota; when both models are limited the errand FAILs with `ai_unavailable` and the log shows `status: 429, code: RESOURCE_EXHAUSTED`.
- A lost job (Redis restart) is now repaired by the errand sweeper (Day 13 amendment).
