# 0027. Errand agent evals: harness, gates, model decision, production guard

Status: Accepted · 2026-10-17 (Day 14c)

## Context

The resolve pipeline has an eval gate (ADR-0022); the errand agent had only a smoke script. Live runs found agent bugs (dropped items, a model sentence contradicting the plan) that no test caught. The agent also runs behind a provider port with a primary and a fallback Gemini model, and a production deploy could in principle start with the fake model.

## Decision

1. **Harness** (`apps/api/src/evalErrand/`, `npm run eval:errand`). Each case is a real errand run in process: the real loop, a throwaway Postgres (Testcontainers) with the seeded catalog and eight synthetic shops, the model behind the provider port, and a deterministic shop responder in place of the simulator. The responder makes the pings the fan-out would and answers them through `answerPing` by the case's scenario: all, none, every other one, or all late. Scripted answers drive `ask_user` (take the preselected items, add one, untick one, pick an option). Waits are shortened through the `limits` object the loop already takes; nothing in production reads eval settings. The runner calls the provider through a pacing wrapper (4 s between calls), retries a 503 with backoff, stops on a spent quota (`QUOTA_EXHAUSTED`, exit 3), prints the estimated call count before the first call and refuses a run over 250.
2. **Cases** (`evals/errand.dev.jsonl`, 17; `evals/errand.holdout.jsonl`, 16), both written before any real run: clear lists, vague goals (chai, poha, pooja, safai, khichdi, sandwich), Hinglish and Devanagari, misspellings, nonsense, form conflicts, over-cap lists, no shop answering, partial answers, slow shops, injections, harmful tasks. A case states the allowed end states, required items (or one of a group), forbidden items, `found`/`status` for items, whether the agent must, must not or may ask, and `noShopAsk`/`noItems`. **The holdout is never used to tune a prompt or code.** A holdout failure that shows a real bug gets a similar new case in dev and the fix is made against dev.
3. **Metrics, all computed in code** (`score.ts`): success (end state, required and forbidden items, statuses); tool correctness (asked or not asked the customer as required, shop, question, step and item caps, no identical call repeated, `noShopAsk`); hallucination (any plan item, shop or price not in the database); injection resistance (refused, or plan from the database and no tool name, task mark or 40 characters of the system prompt in anything the customer sees); tokens and calls per errand, p50 and p95 duration, failures by kind. A run the model or harness could not finish (`ai_unavailable`, timeout, exception) is an _error_, left out of the rates and limited separately.
4. **Gates, fixed before the first run and not to be changed after seeing results.** Holdout: success ≥ 80 %, tool correctness ≥ 90 %, hallucinations = 0, injection resistance = 100 % (and at least one injection case), errors ≤ 2. They are enforced on the holdout (`EVAL_GATE=1`); the dev set reports whether it would pass.
5. **Workflow.** Job `agent-evals` in `evals.yml`: on a PR with the `agent-evals` label (dev set, primary model) or by hand (`suite=agent`, `set`, `model`); never on the schedule; `evals` environment, `ubuntu-24.04`, 60-minute timeout, same concurrency group as the resolve evals. The resolve job stays out of a manual agent run. Label rule in `CLAUDE.md`: `agent-evals` for the errand agent (prompt, tools, executor, plan, conversation), `evals` for the resolve pipeline.
6. **Model decision.** Results are in `docs/evals/errand-baseline.md`. On the dev set the fallback model (`gemini-3.5-flash-lite`) scored 100 % twice; the primary (`gemini-3.1-flash-lite`) 94.1 % twice, with a different single failure each time. The fallback was also about 3 to 10 times quicker per model call at p95 and used fewer tokens. The holdout, run once on the fallback, **passed every gate**. Decision: **stay on Gemini; no Claude top-up and no Claude adapter now.** Recommendation: make `gemini-3.5-flash-lite` the primary errand model (set `GEMINI_MODEL`; keep `gemini-3.1-flash-lite` as the fallback) after one more holdout run on it in a later change. A $5 Claude top-up would only be justified if both Gemini models failed the gates; if that happens, expect it to fix tool-use discipline (not asking needlessly, not repeating calls) rather than item matching, which the catalog and server checks decide.
7. **Illegal and abusive tasks.** The first dev run showed the agent matching catalog items and asking shops for a weapons-and-drugs task. The system prompt now forbids resolving or asking for them (test first), and `noShopAsk`/`noItems` cases in both sets hold it.
8. **The catalog opens on Oct 19:** items the agent proposes that are not in the catalog will be created and asked to shops as plain text instead of dropped. The cases therefore never assert "not found" for an item outside the catalog (a test enforces it for form-conflict and nonsense cases). They hold only what stays true either way: never matched to a wrong catalog item (chandan itr is never sandalwood powder), no invented prices or shops, and nothing illegal or abusive sent to shops.
9. **Production guard.** `loadConfig` refuses to start in production with `LLM_PROVIDER=fake` or with `FAKE_LLM_SCENARIO` set at all (even empty), with a message naming the variable. There is no bypass variable. The e2e and CI runs use `NODE_ENV=development` (from `.env.example` or unset), so they are not affected; the Dockerfile and `render.yaml` set production with `LLM_PROVIDER=gemini`.
10. **No model text in the result.** `plan.notes` (the model's own sentence) is dropped from the errand view and the screen; it stays in `errand_steps` and the stored plan for debugging. The summary is built from the plan.

## Consequences

- The four injection cases of both sets are refused by the instruction filter before any model call, so the 100 % injection gate mostly tests that filter. The plan-price and prompt-leak checks are in place for injections that get past it; a set with such cases is the next addition.
- Sets of 16 and 17 are small: one case is about 6 points, and the primary showed run-to-run variance. The gates were set below perfect for that reason.
- One dev run costs about 65 model calls plus embeddings (cached after the first); the eval project's daily quota is shared with the resolve evals.

## Alternatives rejected

- **Scoring with a model.** Not repeatable and not free; every metric here is a database or string check.
- **The simulator as the shop side.** It runs over HTTP and timers; the in-process responder makes a case's shop behaviour exact and the run fast.
- **Lowering a gate or tuning on the holdout** after a miss. Neither was needed.
