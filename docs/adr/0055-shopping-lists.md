# 0055. Shopping lists: one parchi per shop, binding per line (PR U1, backend only)

Status: Accepted · 2026-10-21 · builds on ADR-0028, 0039, 0043, 0044, 0045, 0046, 0047. Migration 027. No new dependency. Screens follow in U2 and U3.

## Context

A customer who needs six things walks to six shops, or sends six searches and gets six replies. A list is the middle: the customer types up to 10 lines (no AI goal planning, unlike an errand), each shop gets ONE parchi with only the lines it could sell, answers line by line, and the customer orders from several shops at once.

## What we reuse, and why

| From                                                                                       | Reused as it is                                                                                                                                                                                                      | Why                                                                         |
| ------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------- |
| `catalog` free resolver steps (cache, `AMBIGUOUS_WORDS`, exact synonym, trigram, default)  | `findItem` is exported; a list line goes through the same rules, so "maida" is still "Maida" and "mirchi" is still a question                                                                                         | One definition of "understood"; the eval gate already covers it             |
| `catalog` embedding rule (threshold, margin, mostly-words)                                 | extracted into `acceptEmbedding`, used by both paths                                                                                                                                                                 | Same thresholds, no copy                                                    |
| `safety` deny list, `checkProductName`, `looksLikeInstruction`, `cleanItemName`            | run on every line that the free steps did not place, BEFORE any model call                                                                                                                                           | A refused text reaches no model (stricter than the single search)           |
| `ai` client, `limiter`, `markInvalid`, `writeCache`, `suggestSynonym`                      | one `embed` call and one `generateJson` call per list                                                                                                                                                                | The budget in the brief                                                     |
| `requests` `selectPingTargets`, `MISC_FANOUT_MAX` (15), `DEFAULT_RADIUS_M`, `CAN_DELIVER`  | category lines pick their shops with `selectPingTargets` (`maxPings` nearest per line, no backfill); "other" lines take the nearest `MISC_FANOUT_MAX` open shops of any kind. `distanceBand`, `findShopsWithinRadius` (skips closed shops) | Same radius, closed-shop and distance-band rules                            |
| `shops` `recordStockYes`                                                                   | every "have" line teaches learned stock with its price (and the delivery offer)                                                                                                                                      | A list answer fades like any other answer                                   |

| `orders` `delivery_orders`, `lines`, state machine, address rules, `cleanNote`, sweeper    | one order per shop, born ACCEPTED (binding) or REQUESTED, same cancel/dispatch/receive/COD rules; `list_id` is a third source next to `request_id` and `errand_id`                                                    | Delivery v2 is not touched: a list order IS a delivery order                |
| `push` payload builder, notifier, rate limiter                                             | a new kind `new_list` built from plain words; same tag and renotify rules                                                                                                                                            | ADR-0044 stands                                                             |

Not reused: `requests`, `pings` and the fan-out worker. A ping is one shop, one item and one `request_id`; a parchi is one shop and many lines. Bending `pings` would touch every query that joins `requests`, so lists get their own small tables and run their fan-out inside the send transaction (no queue, no per-shop Redis dedupe: one parchi per shop per list is a unique index, and a list is rate-limited per customer).

## Decisions

1. **Limits are shared constants** (`packages/shared/src/lists.ts`): `LIST_MAX_LINES` 10, `LIST_LINE_MAX_CHARS` 80, `LIST_MAX_OPTIONS` 3, `MAX_LIST_ANSWERS` 8, `LIST_TTL_MIN` 15, `LIST_HOURLY_LIMIT` 10. `MISC_FANOUT_MAX` stays in `requests`.
2. **Line cleanup.** Trim, collapse inner spaces, drop empty lines, merge duplicates (case-insensitive, first spelling kept). A line over 80 characters, more than 10 distinct lines, or none at all is a 400 (never silently cut).
3. **Sorting is `POST /lists/sort`** and stores a DRAFT. Each line ends up `item` (with its category), `ambiguous` (up to 3 options; "as I typed" is always also allowed), `other` (no category) or `refused` (`blocked`, `unclear`). At most ONE `embed` request (all lines still unplaced) and ONE `generateJson` call (all lines still unplaced that have a shortlist) per list; no per-line model call. The model sees line text and catalog names only. Its answer is checked per line against that line's own shortlist, so an id it was not offered is dropped. A model outage leaves those lines `other`. The model may also say `blocked` (the layer-2 rule of ADR-0029) because a list line has no classifier call. A list line never creates a catalog item: an unknown line is `other`, a text-only line (no `item_id`, no learned stock).
4. **Sending is `POST /lists/:id/send`** with a choice per ambiguous line (one of its options, or `asTyped`; "as typed" becomes an `other` line). Refused lines are not sent. In one transaction the list becomes OPEN and every parchi is inserted. Category lines go to the nearest `maxPings` open shops in range whose kind sells the item's category; "other" lines to the nearest `MISC_FANOUT_MAX` open shops of any kind. A shop gets ONE parchi with the union of its category lines plus all "other" lines (`other: true` on each, so the shop UI can group them). One `listping.created` event per parchi, so one push per shop per list. A shop that opens later is NOT caught up (follow-up).
5. **What a shop sees:** per line the catalog name (+ the everyday word, ADR-0047), the quantity, "last time you said ₹X", and for an "other" line the customer's cleaned text, which is the item. A distance band, never a position, a name or a raw query. Phone numbers never get that far (`cleanItemName` refuses them).
6. **Listening** ends at `MAX_LIST_ANSWERS` shops answered (any answer, yes or no, counts) or `LIST_TTL_MIN` minutes. At 8 answers the list is `FULL`: unanswered parchis are withdrawn, nobody new can answer, but the answers stay binding. At 15 minutes it is `EXPIRED`. The database deadline is the truth; a read applies it and the 60-second sweeper catches the rest.
7. **Answering is `POST /list-pings/:id/answer`**, once per shop per list (a repeat returns the first answer). Every line of the parchi must be answered and no other: `have` true or false, and a whole-rupee `priceRupees` required with `have: true` and refused with `have: false`. `canDeliver` (refused beyond the shop's own limit, as ADR-0039) and ONE `deliveryFeeRupees` for the whole list. Stored in paise. A withdrawn parchi is 409 `ping_closed` (no late answers for lists; follow-up).
8. **Binding per line.** A ticked line is a promise until the list stops being live (stopped, expired, ordered). Ordering from a live list creates orders born ACCEPTED (no second accept, the shop is pushed "Customer chose you"). Ordering from an EXPIRED list is allowed but not binding: REQUESTED, with the usual 10 minutes. A STOPPED list cannot be ordered from.
9. **Ranking** of answers: number of "have" lines (more first), then distance (nearer first), then total price (cheaper first). Per shop and line: `have` (with price), `no`, or `not_sent` (that shop was never asked about it).
10. **Default plan, exact.** Take the shops that answered with at least one "have". Find the smallest set of them that covers every line that some shop has (at most 8 shops, so all 255 subsets are tried, no heuristic). Among sets of that size choose the shortest route (`planRoute` from the customer), then the lower total, then the lower shop ids. Each line goes to the cheapest shop in the set that has it. Lines no shop has are `missing` ("nobody has this yet"). The plan is worked out on every read from the answers; nothing about it is stored.
11. **Ordering is `POST /lists/:id/order`**, all or nothing in one transaction under the list's row lock: the customer sends `assignments` (line to shop) and a `mode` per shop. Every assignment must be a line that shop said it has; `delivery` only if that shop said `canDeliver`; delivery needs an address (typed, or the saved one, as ADR-0039); a closed shop refuses the whole call. One delivery order per delivery shop with prices and the fee from its own answer. A shop set to `pickup` gets no order (as in errand plans: pickup is the customer walking there); the response echoes those lines. The list becomes ORDERED.
12. **Packing.** Each order line has a `packed` flag. `PUT /orders/:id/lines/:index/packed {packed}` is the owning shop's only, while the order is not final. It works for single-search and errand orders too. The shop view has `packedCount`, `lineCount` and `unpackedCount`; `POST /orders/:id/out` is allowed with unpacked lines and its response says how many.
13. **Stop asking.** A single search already has `POST /requests/:id/close`; lists get `POST /lists/:id/stop`. Both stop new pings, withdraw open ones, and make existing answers non-binding (REQUESTED if still ordered from). Both end what `DELETE /account` checks, so the account can then be deleted (`hasLiveList` joins `hasLiveRequest`).

## Consequences

- Delivery v2, the errand pipeline and the single search are unchanged except: the resolver's free steps and embedding rule are exported for reuse, `delivery_orders` gains `list_id` and a `packed` flag per line, and the shop order view gains packed counts.
- Cost per list: at most 1 embedding request and 1 generation call, whatever the number of lines.
- `evals/resolve.list.dev.jsonl` holds list sorting cases (dev only, never gated) and a test fails if a list makes more than one `generateJson` or one `embed` call.

## Alternatives rejected

- Making a list a set of `requests` (one per line) and grouping pings per shop at read time: N fan-outs, N pushes unless suppressed, and no single "answered" moment for a shop.
- The classifier call per unknown line (creating catalog items): breaks the one-call budget and floods the new-item daily limit of 10 with a single list.
- Closing the list at 8 answers AND making the answers non-binding: the eighth reply would void the first seven while the customer is still comparing.
- Approximate set cover: at most 8 shops means 255 subsets; exact is cheap and explainable.
