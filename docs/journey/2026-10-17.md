## Evals workflow: fail fast on quota, run on a schedule, pin the runner

- **What:** `evals.yml` runs daily at 08:30 UTC, on the label and by hand (no push to `main`), 30-minute timeout; `modules/ai/quota.ts` (`rateLimitInfo`, `QuotaWatch`, `watchProvider`) + `ProviderError.rateLimit` set by the Gemini adapter; `evalResolveMain.ts` preflights and stops with `QUOTA_EXHAUSTED` (exit 3); all jobs on `ubuntu-24.04`, actions on Node 24 majors; runbook, ADR-0022 note, evals.md, changelog.
- **How:** test commit first (classification of Google's 429 body, the watch's rules, the adapter), then the code. The action versions came from the actions' releases and the `runs.using` line of each `action.yml`, not from memory.
- **Why:** a run that cannot finish should say so in seconds. I put the check in a provider wrapper so every call (resolve, errand, embedding) is seen without touching the retry client. Rejected: stopping on any 429, because per-minute 429s are normal and clear on their own.
- **Learn:** a free quota has windows (minute, day); retrying only helps when the wait is shorter than the window. Read which window was hit before deciding to retry.

## Day 14c part 1: "chandan itr" is not sandalwood powder

- **What:** `modules/catalog/productForm.ts` (curated forms, `formConflict`) used by `resolve.ts` at every step and by `errands/plan.ts`; `CATALOG_VERSION` hashes the form list; `progress.ts` wording (soft "pichhle jawabon mein nahi mili" until the shops answered) with `requestId` on answers; web summary (`ErrandResult.tsx`, strings in both languages), notes moved into "Ab tak kya hua"; seven `form` cases in the dev eval set; ADR-0021 amendment, BRIEF, CHANGELOG.
- **Root cause:** the **trigram** step. "chandan itr" scored 0.67 against the catalog term "chandan powder", was the only candidate (no rival within the margin), and the matched term was long enough (coverage 0.64 ≥ 0.6), so it passed every check built for typos and nonsense. None of those checks asks whether the two words mean the same product. The cache was not involved (the free steps answer before anything is cached, and the AI steps never ran), but a cached wrong answer from the LLM or embeddings would have come back for 30 days, so cache reads are guarded too and the version changed.
- **How:** test commit first (unit for the form list, an integration test per step with a planted wrong synonym, default and cache row, embeddings and LLM stubs, an errand test, progress and web tests), then the guard.
- **Why:** a general rule on product form instead of a fix for "itr": gulab itr and sarson tel are the same bug. The item's form comes from its names only, not synonyms, so a wrong synonym row cannot approve itself. Rejected: asking the LLM to notice (the trigram match never reaches it).
- **Learn:** "similar spelling" and "same product" are different questions; a fuzzy match needs a check on what must not differ (here the form), not only a threshold on how alike the words look.

## Day 14c part 2: agent evals, model decision, production guard

- **What:** `apps/api/src/evalErrand/` (cases, score, run, pace, prepare) and `evalErrandMain.ts`; `evals/errand.{dev,holdout}.jsonl`; `agent-evals` job and dispatch inputs in `evals.yml`; config refuses the fake model in production; `plan.notes` removed from the errand view and screen; prompt rule for illegal tasks; ADR-0027, `docs/evals/errand-baseline.md`, runbook, BRIEF, CHANGELOG, CLAUDE.md label rule.
- **How:** both case files and the gates were committed before any real run; test commit first (scoring, case files, workflow, config, view, harness with a fake model), then the code. The runs were made in CI. Dev: primary 94.1 % (d17, a harmful task, asked shops), fallback 100 %. The failing case was fixed against dev (prompt rule, test first); the holdout was run once, on the fallback model, and passed every gate (100 % success and tool correctness, 0 hallucinations, 2/2 injection, 0 errors). The holdout exposed nothing and was not used for tuning.
- **Why:** the model proposes and the database decides, and a live example proves it: the model wrote "Shiv Kirana Bhandar mein sarson ka tel mil jayega" before a later answer arrived, while the plan picked Gupta Kirana Store (₹168 against ₹195). Its sentence was wrong the moment the facts moved, so the screen now shows only the summary built from the plan, and the sentence stays in `errand_steps` for debugging. Rejected: tuning on the holdout, a model-scored metric, and a bypass for the production guard.
- **Learn:** an eval is only as honest as its separation: the set you tune on and the set you judge on must never be the same, and every metric must be computable without a model. Also read what a perfect score is made of: here the injection cases are all caught by a filter before the model sees them, so 100 % says little about the model.

**Follow-up before merging PR #28: a model per purpose.** The provider had one model and one fallback for both query resolution and the errand agent, so switching errands to `gemini-3.5-flash-lite` would also have moved resolve off the model its gate was proven on. The AI client now takes a model per purpose; `GEMINI_ERRAND_MODEL` and `GEMINI_ERRAND_FALLBACK_MODEL` apply to errands only and default to the shared ones. Test first (config, client, harness mapping). Earlier harness runs set `GEMINI_MODEL`, so resolve inside those runs used the fallback model too; the final dev run uses the errand setting only. Lesson: a shared setting is a coupling; check what else reads it before changing it.
