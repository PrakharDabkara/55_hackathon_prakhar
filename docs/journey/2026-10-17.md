## Evals workflow: fail fast on quota, run on a schedule, pin the runner

- **What:** `evals.yml` runs daily at 08:30 UTC, on the label and by hand (no push to `main`), 30-minute timeout; `modules/ai/quota.ts` (`rateLimitInfo`, `QuotaWatch`, `watchProvider`) + `ProviderError.rateLimit` set by the Gemini adapter; `evalResolveMain.ts` preflights and stops with `QUOTA_EXHAUSTED` (exit 3); all jobs on `ubuntu-24.04`, actions on Node 24 majors; runbook, ADR-0022 note, evals.md, changelog.
- **How:** test commit first (classification of Google's 429 body, the watch's rules, the adapter), then the code. The action versions came from the actions' releases and the `runs.using` line of each `action.yml`, not from memory.
- **Why:** a run that cannot finish should say so in seconds. I put the check in a provider wrapper so every call (resolve, errand, embedding) is seen without touching the retry client. Rejected: stopping on any 429, because per-minute 429s are normal and clear on their own.
- **Learn:** a free quota has windows (minute, day); retrying only helps when the wait is shorter than the window. Read which window was hit before deciding to retry.

## Day 14a: plan quality (optimiser, truthful names, multi-category items, catalog gaps)

- **What:** `modules/errands/optimiser.ts` (two plans, `recommend`), `matchedAs.ts`, `plan.ts` rebuilt on them, `progress.ts` (Samjha count, "Aapne 'diya' kaha tha" lines); migration 013 `items.categories`, `targets.ts` overlap, seed v5 (55 items, extra categories on 61 items, `dhoop` split from incense), `ERRAND_FEWER_STOPS_MAX_EXTRA_PAISE`, ADR-0025, brief, changelog, `~/kahan-tools/errand_test.sh`.
- **How:** test commit first (optimiser, matched-as, progress, targets, seed, two integration suites), then the catalog and categories, then the optimiser and plan wiring. Old tests that asserted "a made-up shop becomes not_found" changed on purpose: the plan now ignores the model's shop. Smoked on the local API and simulator with Gemini.
- **Why:** choosing shops is arithmetic, so it moved to tested code and the model only lists items. Kept `items.category` next to `categories` (one check ties them) instead of dropping it; rejected a blended score because rupees and stops have no honest exchange rate.
- **Learn:** an exact search beats a greedy one when the input is small: set cover is hard in general, but with 10 items "pick the item with the fewest options and branch" finishes instantly and is provably the fewest shops.
