## PR Q: rename to AskBuy, brown sugar, shop tagline

- **What:** `@kahanmilega/*` → `@askbuy/*` everywhere; MCP server/bin/env/login file; errand prompt; CI and local compose; BRIEF, README, runbook, CLAUDE.md, CHANGELOG, scenarios; ADR-0051, ADR-0052, `docs/naming.md`; `evals/naming.test.ts`; brown sugar out of `denyList.ts` and into `catalog.seed.json` (v8); shop login tagline (en/hi).
- **How:** tests first (red), then the brown-sugar and tagline fixes, then a mechanical package rename (sed + `npm install`, lock diff is names only), then code/CI/compose, then docs. Local data proved by `db:up` under the new project name: same volume, 24 migrations still there.
- **Why:** rename all that is safe, keep what would log users out or break deploys (URL, DB names, storage keys, Redis channel, eval cache). A guard test keeps the keep list honest. Rejected: renaming the Redis channel (drops events mid-deploy) and the eval cache (full re-embed on the quota).
- **Learn:** a Docker Compose project name is derived from the folder and prefixes volume names; renaming the project would orphan data unless volumes get explicit names.

## PR R: new named items are confirmed

- **What:** `modules/errands/{executor,agent,conversation}.ts` (rule 3, `checklistFor` option, `unconfirmedNew`), `evalErrand/{cases,score,run}.ts` (`offeredAny`), `evals/errand.dev.jsonl` (d18 only), tests `errandNewNamed.int.test.ts`, `checklist.test.ts`, `score.test.ts`, ADR-0053, scenarios S33, CHANGELOG.
- **How:** `resolve_item` remembers words that came back new or unresolved; after each turn, if the customer named one and has not ticked or unticked it, the server asks the checklist (named first and ticked, the agent's extras unticked). `ask_shops` on a new item needs a tick, not just a mention. The eval harness records the options shown and the scorer checks them.
- **Why:** a named new item was "confirmed" by being named, so no question came (d18). Rejected: changing the prompt (model-dependent, ADR-0049 chose code) and un-ticking rule 2's list too (a goal-only task has nothing the customer named, so review needs the list ticked).
- **Learn:** a guarantee that must always hold belongs in code that checks state, not in a prompt that asks the model to remember it.

## CI red on main after #49: the e2e job shared the dev volumes

- **What:** `docker-compose.yml` volume names read `PGDATA_VOLUME` / `REDISDATA_VOLUME` (defaults unchanged); the CI e2e job sets its own and runs `docker compose down -v` first; `evals/ciVolumes.test.ts`; CHANGELOG.
- **How:** read the failed run's artifacts (the replies page said "Sent to 0 shops", sugar was already known), then reproduced it: the same database passes once and fails every run after. Pinned the names with a test, then ran seeker three times and the full suite on fresh CI volumes.
- **Why:** compose volumes have fixed names, so project `askbuy-ci` still mounts `kahanmilega_pgdata`; a reused database carries learned stock. Rejected: making seeker pick another item (loosens the test, hides the shared data) and a longer timeout.
- **Learn:** a compose project name does not isolate a volume that has an explicit `name:`; isolation needs the volume name itself to differ.

## PR S: customer Account screen

- **What:** `/app/account` (`screens/Account.tsx`, `customer/account.css`, header person icon in `Home.tsx`), `modules/account` (`GET /account`, `POST /account/logout`, `DELETE /account`), migration 026, `lib/theme.ts` + `public/theme-init.js`, dark tokens under `[data-theme]`, ADR-0054, tests (`account.int.test.ts`, `Account.test.tsx`, `e2e/account.spec.ts`).
- **How:** tests first (API, screen, e2e). Delete locks the user row, checks open orders, live requests and errands, then erases subscriptions, saved address, sessions and the phone in one transaction; the row stays so orders keep a user. Logout carries the push endpoint so the token and the subscription end together. The theme is `data-theme` on `<html>`, set by a small file before first paint.
- **Why:** soft delete keeps shops' records; hard delete would break orders (a rejected alternative: deleting the user row, which cascades to orders). The first-paint script is a file because the CSP forbids inline script; loosening the CSP was the rejected option. The "What shops can see" draft said "never your name": the order form has an optional name, so the text was corrected, not the behaviour.
- **Learn:** anonymising is not deleting. Keep the row that other records point at, erase what identifies the person, and make the unique key (the phone) free again by making it NULL, because UNIQUE allows many NULLs.
