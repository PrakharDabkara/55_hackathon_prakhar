## PR U1: shopping lists, backend only

- **What:** `modules/lists/*` (sort, send, answer, stop, order, view, exact cover, ranking), `catalog/resolveList.ts` and `ai/resolveListPrompt.ts` (batch sorting), `orders` (`list_id`, packed lines, `insertListOrders`), migration 027, push kind `new_list`, simulator `decideList`, `evals/resolve.list.dev.jsonl`, ADR-0055, scenarios S35 to S45.
- **How:** read the request, order, errand and resolver code first and wrote down what to reuse (ADR). Tests first for the pure parts (line cleanup, ranking, exact cover, answer and order checks), then HTTP tests for fan-out, the 8 and 15 minute limits, atomic ordering, packing and stop. A list line goes through the resolver's own free steps, then ONE `embed` and ONE `generateJson` for the lines still unplaced; the model's answer is checked per line against that line's own shortlist.
- **Why:** a list is its own small set of tables, not many `requests`: a parchi is one shop with many lines, and a request is one item. Lines nobody can file stay text-only ("other"), so no catalog item is made and the one-call budget holds. Rejected: a classifier call per unknown line (breaks the budget and the daily new-item limit) and closing at 8 answers while also voiding them (the eighth reply would cancel the first seven).
- **Learn:** an exact search beats a clever heuristic when the input is bounded: at most 8 shops means 255 subsets, so "fewest shops" is checked, not guessed, and a tie-break (route, then price) makes the answer repeatable.

## PR U1 follow-up: pickup orders for lists, customer push for list answers

- **What:** migration 028 (`fulfilment`, READY and COLLECTED, pickup is anonymous check), order state machine/service/views/routes (`ready`, `collected`), `lists/service.ts` (an order per shop), push kinds `list_answered`, `list_ready`, `order_ready`, simulator readies pickups, ADR-0055 rules 11, 14, 15, scenarios S46 to S49.
- **How:** tests first (state machine table, payloads, HTTP and push scenarios), then the migration and the code. The machine stays a table of states; the order service checks which tap fits delivery or pickup. The list notification is built from `list.updated` events and the database counts, so the same code handles an answer, the 8th answer and the sweeper's expiry.
- **Why:** a pickup that makes no order leaves nothing to pack and nothing to end. A CHECK constraint makes "a pickup holds no address or name" a fact of the database, not a habit of the code. Rejected: a separate pickups table (a second order lifecycle, a second sweeper) and putting the fulfilment into the state names.
- **Learn:** put a privacy rule where it cannot be forgotten: a constraint on the table beats a view that is careful.

## PR V: reliable evals

- **What:** `modules/ai/timeout.ts` (30 s per request), retry cap and Retry-After in `client.ts`, `evalProgress.ts`, `evalQuota.ts`, `evalEmbeddings.ts`, both eval mains, `evals.yml`, runbook, CHANGELOG, tests.
- **How:** tests first (hang, retry cap, Retry-After, daily quota, progress, workflow). Then one wrapper for the timeout, a pure pause function in the client, small helpers shared by both runners.
- **Why:** the stalls were nested retries (client 5 retries x 30 s inside 2 runner retries) plus unguarded preflight calls and a cache saved only at the end. I rejected a global wall-clock kill inside the scripts: the job timeout already does that.
- **Learn:** retries multiply when layered; give each layer a budget, and let the outermost deadline (the job timeout) be the last resort, not the first.
