## Day 10: evals as a CI gate, resolution fixes, Day 8 polish

- **What:** dev set, retired holdout v1 and holdout v2; eval runner with categories, gates, step summary and a Testcontainers database; `evals.yml` workflow; `defaultFor` step, nonsense guard, typo edit-distance guard, first-line cleaning and an instruction-pattern check; cache expiry and catalog version; admin cache delete; migration 009; status line with the no count, map refit, login link; install-script policy; ADR-0022, `docs/evals.md`, runbook, brief.
- **How:** test commits first (the holdout files each in a commit of their own, before any run). Two CI runs on holdout v1 failed a gate for real ("guitar" resolved to glitter); I did not edit v1, retired it, fixed the causes in general ways and wrote a fresh v2. v2 passed on its first run, at 91.8 % against a 90 % gate.
- **Why:** a score on data you tuned on is a training score, so the gate runs on queries nobody looked at. "Guitar" matched a misspelling synonym in our own catalog ("glitar") one keystroke away, which no edit-distance rule can reject; the synonym went. Rejected: gating on every PR (cost) and on the dev set (memory).
- **Learn:** a holdout stops being one the moment it informs a fix, so retire it and write a new one. And a free-tier quota counts every embedded text, so a CI job that re-embeds a catalog on each run spends the day's budget fast; GitHub's cache is scoped per branch or PR, so check it actually hit.

## Day 10, later: making the gate honest about noise

- **What:** the eval runner retries a failed model call twice and counts a query that still fails as an error (own column, not scored); gates are now accuracy ≥ 85 %, injections 100 %, no nonsense resolved, LLM fallback ≤ 40 %, errors ≤ 3; latency is the provider call only; the workflow runs on the `evals` label, by hand and on push to `main` (no path filter); CLAUDE.md requires the label; docs and ADR-0022 updated.
- **How:** tests first for the scoring (errored rows leave accuracy, the errors gate, the 85 % boundary), then the runner. I recomputed both existing holdout-v2 runs from their saved reports under the new gates instead of spending quota: both pass.
- **Why:** two runs of the same code scored 91.8 % and 88.5 %, so a 90 % gate fails good code at random. I rejected best-of-N (it hides noise) and chose a threshold below the observed range, with a separate error gate so a dead API cannot pass. I left the generic-word weakness unfixed: those words came from v2, so fixing them now would tune on the test.
- **Learn:** a path filter on a pull request looks at the whole diff, not the last push, so it re-runs on every push; an explicit label is a cheaper, clearer trigger. And a threshold should come from measured variance, not from a round number.

## Day 12: Errand agent core

- **What:** `modules/errands` (loop, in-process tools, plan check, state machine, persistence, progress, API), `LlmProvider.chatWithTools` (Gemini function calling, fake scripted turns, `ai_calls` purpose `errand`), migration 010 (`errands`, `errand_steps`), BullMQ `errand` worker, `ERRAND_*` config, `npm run errand:smoke`, ADR-0024, BRIEF, runbook, changelog.
- **How:** test commit first (provider port, tools, state machine, progress, prompt, then an integration suite on a real database with a scripted model: one item, three items with one missing, a claimed shop without stock, made-up ids, step and token caps, an injection, a provider error, two runs at once). Then the code. Then two real Gemini runs: both reached PLAN_READY in 10 steps, about 6,700 tokens each; the first attempt hit Gemini 503s and failed gracefully, so the retry count became a setting.
- **Why:** the model only proposes; `submit_plan` is checked against the database, so a hallucinated shop or price cannot reach the user. The loop is ours (about 150 lines) because the caps, the log and Day 13's resume are the product. I rejected an agent framework (hides the loop) and a Postgres enum for state (Day 13 adds states; a CHECK constraint is cheaper to change).
- **Learn:** treat an LLM's output as a claim, not a fact: let it choose among options your code offers, then re-derive every fact (price, stock, distance) from your own records before showing it. A budget works only if the code enforces it and the model is merely told.

## Fix: errand AI reliability (live errands failed with ai_unavailable)

- **What:** AI failures now log `purpose, model, attempt, kind, status, code, latencyMs, message` and store the kind in `ai_calls.outcome` (migration 011); errand calls get `ERRAND_AI_TIMEOUT_MS` (30 s) while resolve keeps 8 s; `GEMINI_FALLBACK_MODEL` (`gemini-3.5-flash-lite`) for attempts after a timeout, 429 or 503; one breaker per purpose; `GET /admin/ai/ping`; runbook troubleshooting; ADR-0024 amendment.
- **How:** tests first for each kind, per-purpose timeouts, fallback rules, breakers, ping and the Gemini error classification, then the code. Then I measured: the 8 s limit was the cause (a first errand call took 21 s; 503s themselves take up to 12 s to arrive), and I chose the fallback by a burst of eight calls per candidate model, not by name.
- **Why:** a failure you cannot read is a failure you cannot fix: the same word (`kind`) is in the log line, the database and the ping answer. A fallback must have its own capacity: the fastest model I tried (`gemini-3.5-flash`) is useless as one because its free quota is tiny; I rejected a preview of the primary's own family for sharing its capacity.
- **Learn:** a timeout is a policy per kind of work, not one global number: a small JSON classification and a tool-calling planning step have different normal latencies. And free-tier limits differ per model, so measure a burst before trusting a model name.

## Day 13: errand agent patience (ask shops, wait, resume, ask the user)

- **What:** `ask_shops`, `get_request_status`, `ask_user`; states `WAITING_FOR_SHOPS`, `NEEDS_INPUT`, `EXPIRED`, `CANCELLED`; wake-up by replies/timer/sweeper; `/errands/:id/answer` and `/cancel`; `confirmed` backed by a yes in the errand's own requests; progress lines and `errand.updated` hints; `/admin/errands/stats`; migration 012; files in `modules/errands` (`agent`, `persistence`, `service`, `wake`, `conversation`, `bridge`, `stats`), `workers/*`, `realtime.onPublish`; ADR-0024, BRIEF, runbook, changelog.
- **How:** test commit first (state × event table, tools, progress, config, then a 46-test integration suite on real Postgres with a scripted model and a real Redis for the lost-job case). Then the code. Then two real Gemini runs with the simulator: both reached PLAN_READY (62 s and 88 s, about 14,000 and 16,500 tokens, 14 steps each, waits of 45 s); a third attempt failed on Gemini 503s until the fallback model was set.
- **Why:** the log is the conversation, so a run can die anywhere and the next one rebuilds the same messages, thought signatures included. The wake-up is one guarded UPDATE with the "is it time" test inside it, so the timer, the answer hook and the sweeper can all fire and still resume once. I rejected a `wait` tool (the shape of the turn already says it) and fake function-call parts for the status (Gemini checks signatures on its own calls).
- **Learn:** make the database the single arbiter of "who acts now": put the condition inside the UPDATE ... WHERE, and every trigger (timer, event, sweeper, retry) becomes safe to fire twice, so you can add triggers freely instead of adding locks.
