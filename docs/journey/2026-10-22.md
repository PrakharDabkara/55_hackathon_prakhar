# 2026-10-22

## Day 11: MCP server and one tool registry

- **What:** `packages/shared/src/tools` (six tool definitions), `apps/mcp-server` (API client, handlers, stdio server, login, token file), `modules/routing` and `POST /route/plan`, optional `q` with an `itemId`, scripts `mcp:build|login|start`, ADR-0023, README section, brief.
- **How:** test commit first for everything: the registry (names, flags, descriptions, schemas), the route planner (checked against a brute force over all orders), the API additions, the HTTP client, every handler against a fake API (including each error status), the token file and the login flow, then a contract test that runs the real MCP server through the SDK's in-memory client against the real API on Testcontainers, including ask, a simulated shop answering, then status and close. Then the code.
- **Why:** the tool's description is the AI's only instruction, so tools are data (name, description, schemas, side-effect flags) in one place that both the MCP server and Day 12's agent read; only the executor differs. The MCP server is a plain HTTP client of the public API with the user's token, so an assistant can do exactly what the customer could, no more. I rejected a single do-everything search tool (an AI could ping shops unintentionally) and an MCP server with database access.
- **Learn:** an AI-facing interface needs more than types: it needs the right words (when to use, what next), declared side effects, and errors written as instructions ("run npm run mcp:login"). Also, a shared package that web also imports must not pull heavy dependencies: putting the registry behind a subpath kept the web bundle at 400 kB instead of 487.
