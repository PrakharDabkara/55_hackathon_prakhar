## Day 11: MCP server and one tool registry

- **What:** `packages/shared/src/tools` (six tool definitions), `apps/mcp-server` (API client, handlers, stdio server, login, token file), `modules/routing` and `POST /route/plan`, optional `q` with an `itemId`, scripts `mcp:build|login|start`, ADR-0023, README section, brief.
- **How:** test commit first for everything: the registry (names, flags, descriptions, schemas), the route planner (checked against a brute force over all orders), the API additions, the HTTP client, every handler against a fake API (including each error status), the token file and the login flow, then a contract test that runs the real MCP server through the SDK's in-memory client against the real API on Testcontainers, including ask, a simulated shop answering, then status and close. Then the code.
- **Why:** the tool's description is the AI's only instruction, so tools are data (name, description, schemas, side-effect flags) in one place that both the MCP server and Day 12's agent read; only the executor differs. The MCP server is a plain HTTP client of the public API with the user's token, so an assistant can do exactly what the customer could, no more. I rejected a single do-everything search tool (an AI could ping shops unintentionally) and an MCP server with database access.
- **Learn:** an AI-facing interface needs more than types: it needs the right words (when to use, what next), declared side effects, and errors written as instructions ("run npm run mcp:login"). Also, a shared package that web also imports must not pull heavy dependencies: putting the registry behind a subpath kept the web bundle at 400 kB instead of 487.

## PR W: simulated shop removal under contention

- **What:** `modules/simulation/service.ts` retries the removal on deadlock (40P01/40001, 3 tries) and maps database errors to `sim_remove_busy` / `sim_remove_failed`; tests in `remove.test.ts` and `admin.int.test.ts`.
- **How:** CI log had only `internal`, so I read the migrations (every list table cascades), ran the suite 6 times (no repro), wrote the list-data test (passes unchanged), then tests for retry and codes, then the code.
- **Why:** the foreign-key theory was wrong; the only cause I can name is a race under CI load, so I made the endpoint safe to retry and its errors readable. Rejected: new deletes for list tables, which cascade already.
- **Learn:** SQLSTATE 40P01 means the database chose your transaction as a deadlock victim; the right answer is to run it again, not to fail.

## PR SEC2: API hardening (branch sec/api-hardening, ADR-0059)

- **What:** `http/routeLimits.ts`, `http/securityHeaders.ts`, `http/ipLimit.ts`, `app.ts`, config (`RATE_LIMIT_SCALE`), every `modules/*/router.ts` (strict schemas), push host list, photos `Cache-Control`, `identity/middleware.ts`, simulator `client.ts`, e2e config, ADR-0059, CHANGELOG, and the tests (`apiHardening.int.test.ts`, `http/*.test.ts`, `pushEndpoint.test.ts`).
- **How:** tests first (limits, headers on 404/400/429, CORS and cookies, error bodies, push hosts, a two-customer/two-shop matrix over every `:id` route, a scan that forbids `z.object` in route files), then the code. The matrix found no ownership hole; the real gaps were limits, headers, push hosts, unknown fields and a few unbounded strings. Then the existing suites showed what the limits cost: 74 int tests and the e2e run hit 429, so a `RATE_LIMIT_SCALE` multiplier lifts them for tests (production refuses more than 1).
- **Why:** one middleware in front of the routers, keyed on the user id, instead of a limiter inside eight routers; `strictObject` plus a source scan instead of remembering `.strict()`. Rejected: `helmet`, `cors` and `express-rate-limit` (not in the brief).
- **Learn:** a limit keyed on the token is no limit: a second login is a second token. Key on what you want to protect (the user) and, separately, on the network address.

### SEC2 follow-up: the simulator's request rate

- **What:** `apps/simulator/src/rate.int.test.ts` (a measurement, skipped unless `MEASURE_SIM_RATE` is set), ADR-0059 and CHANGELOG notes. No code change to the limits.
- **How:** the real API over HTTP with a counting limiter store; 10 simulated shops at real speed answering 15 single requests, a list and a delivery order for 3 minutes, the customer from another address. Counted the hits on the per-IP baseline key.
- **Why:** you asked for an exemption only above ~150 a minute. The simulator's peak was 17 (customer side 29), so an exemption would add a way round the limit for nothing. Fan-out caps answers per search at 10, so more shops do not mean more calls.
- **Learn:** measure the demand before building the exception; a rate limit's cost is the traffic you actually have, and here the headroom is about 17 times.
