## Day 17, PR J: Delivery v2 (ADR-0039)

- **What:** migration 022; `wants_delivery` and a saved-address pointer on requests and errands; `canDeliver` and `delivery_max_km`; fresh offers start ACCEPTED; one live order per request; customer `received`, `NOT_CONFIRMED`, shop cancel with a reason, an order note; web (Find checkbox, three shop answers, Received, cancel), simulator, e2e and scenarios S16 to S21.
- **How:** read the code first and found where the brief and the repo differed (one saved address with no id, no `OFFER_FRESH_MINUTES`, no order queue job, first yes closes other pings), asked three questions, then red tests (backend, then web), then code. Every transition stays a guarded `UPDATE … WHERE state = from`; the new deadline is a column read by the sweeper and by any read.
- **Why:** the customer, not the shop, knows the goods arrived; and a unique index decides "one shop" even when two taps race. Rejected: a queue job for a 3-hour deadline, role-based cancel (one user can be shop and customer).
- **Learn:** a rule about "one of many" belongs in a unique index, not a check before the insert: the check is a read, and two requests can both pass it.

## Day 17, PR K: shop-screen data and shop logo (ADR-0040)

- **What:** `lastPricePaise` on ping cards (`pings.ts`); `?days=1|7`, `avgReplySeconds` (`demand/`); shop logo with migration 023 (`photos/logo.ts`, `photos/router.ts`, `shops/service.ts`); `logoUrl` in results and order views; `testing/truncate.ts` and ~20 test files.
- **How:** red tests first (one commit), then the code. The new foreign key `shops.logo_photo_id → photos` made `TRUNCATE requests … CASCADE` wipe `shops` and failed 16 old tests; I found it by checking the shops table inside a failing test, asked which fix, and added a truncate helper.
- **Why:** the logo reuses `photos` so the size, type, metadata and storage rules stay in one place. Rejected: a separate logo table (a second copy of all that) and a plain uuid with no foreign key (the database would stop clearing it).
- **Learn:** `TRUNCATE … CASCADE` follows every foreign key, not the data: adding one reference can empty a table that looks unrelated. A cache header can be "forever" when the URL changes with the content.

## Day 18, PR L: Parchi shop UI (ADR-0041)

- **What:** the whole shop app restyled and rebuilt under `apps/web/src/shop/` (`ui/` primitives, parchi and deck, `screens/` for login, set-up, home deck, answer sheets, orders, insights, delivery, settings, notifications); `design/tokens.css`, `brand.ts`, self-hosted fonts; the web app defaults to English; `ShopApi` gains `updateShop`, `uploadLogo`, `deleteLogo`, `shopDemand(days)`; the old shop screens are deleted; new e2e `shop-screens` (screenshots and axe) and `shop-setup`.
- **How:** read the API first and found that no field was missing, only names (`feePaise`, `cancelReason`, no `total`), so the client maps them and the backend is untouched. Tokens are scoped to `.shop-app` because the customer stylesheet still owns `--ink`, `--paper`, `--line` and `--tap`. The map is the one file that touches Leaflet, so every screen tests without a real map.
- **Why:** one `useShopData` hook feeds every screen (events are hints, a poll is the safety net), so counts in the menu and the deck never disagree. Rejected: a router library (a hash is enough and Back works) and tokens on `:root` (they would have repainted the customer app). The torn edge needs `at top`, not the `at bottom` in the brief, or the teeth land on the bottom edge.
- **Learn:** a guard against a double tap has to remember what was sent, not only that a send is in flight: the first answer can come back before the second tap lands, so "busy" is already false. Key it by order, action and state, and clear it when the send fails.
