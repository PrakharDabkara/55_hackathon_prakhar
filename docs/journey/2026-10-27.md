## PR: sign-in limit order and limiter fallback visibility

- **What:** Ordering regression test for `POST /auth/otp/request`; the IP limiter logs and counts fallbacks from Redis to memory (`limiterFallbacks.ts`, `limiter.fallbacksToday`); `verify-live-security.sh` check 3 spends the budget itself; ADR-0058, limits and runbook updated with the hops=2 experiment.
- **How:** read the middleware order (limiter first already), the config (limit 10, production refuses more) and the deployed sha (same as main) before touching anything; tests first; the script was run against a fake server that shares or splits buckets.
- **Why:** the first hypothesis (a higher live limit) was refuted by the code, so no limit change; the split counters are only suspected, so the PR adds the logging that proves or kills it instead of guessing a fix.
- **Learn:** a fixed-window counter keyed by IP only works if every request reaches the same counter; a fallback store that quietly starts at zero splits the budget.
