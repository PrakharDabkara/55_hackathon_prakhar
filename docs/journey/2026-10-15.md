## Product direction: errand agent

- **What:** `docs/BRIEF.md` (summary, Errand flow, states, agent row, metrics, 18-day plan, Later list), ADR-0011, ADR-0012, CHANGELOG. Docs only; branch `docs/agent-direction`.
- **How:** Edited the brief in place, keeping the Decisions table and ticked days; added the Errand flow, state machines and agent guardrails; rewrote Days 4–18 with dates and gates; wrote the two ADRs.
- **Why:** One-item search is weak value and depends on shop replies; an agent that plans a whole task is the centre, with shop delivery as a stretch. Rejected a runner fleet (Dunzo, Swiggy Genie) and an agent framework (a small own loop is easier to eval and cost-track).
- **Learn:** A durable agent keeps state in the database and is resumed by a job, so no LLM call or process waits on slow shops.

## Day 4: identity and shops

- **What:** Migration 003; `modules/identity` (phone, OTP rules, tokens, service, middleware, router) and `modules/shops` (service, router); `packages/shared` constants; `http/errors.ts`, `db/queryable.ts`; config `OTP_MODE`; Dockerfile, `render.yaml`, `.env.example`; ADR-0013.
- **How:** Test commit then implementation commit for shared constants, config, the pure rules, and the API (26 Testcontainers tests for the whole flow). Built the Docker image and ran it against local Postgres.
- **Why:** Session tokens are random and stored hashed, so logout is one row update; rejected JWT (no revocation, extra dependency). The OTP attempt is counted before the code is compared, in one SQL update, so parallel guesses cannot beat the limit of 5.
- **Learn:** Count-then-insert is a race under READ COMMITTED even inside one statement: concurrent statements cannot see each other's uncommitted rows. It needs a lock (advisory lock, row lock via UPDATE, or SERIALIZABLE). An UPDATE with a WHERE guard is safe because Postgres re-checks the row after waiting for the lock. The OTP request limit failed a 10-parallel test 4 runs in 5 before the advisory lock.

## Day 5: catalog and search v1

- **What:** Migration 004; `modules/catalog` (normaliseQuery, resolveItem, seed + 223-item `catalog.seed.json`), `modules/shops` (stock rules, `findLearnedStock`), `modules/search` (`GET /search`); `npm run seed:catalog` and a deploy step; ADR-0014.
- **How:** Test commit then implementation for each piece: the pure functions, the seed file checks, then a Testcontainers suite (3+ shops at known distances and ages, expired stock, radius, unresolved queries). Seeded the local database twice to confirm the upsert is idempotent.
- **Why:** Dictionary first, then `pg_trgm`, then (Day 9) AI: the cheapest path answers most searches for free. Rejected an npm fuzzy library: it adds a dependency and holds the catalog in API memory. Every query is logged, and the unresolved ones become the Day 9 eval set.
- **Learn:** Trigram similarity compares overlapping 3-letter chunks, so it forgives typos in long words but is weak on short ones ("aata" vs "atta" scores 0.25); that is why common spellings are listed as synonyms and fuzzy matching is only the safety net.

## Fix: ambiguous catalog terms

- **What:** `catalog.seed.json` (36 terms removed, `paper-clips` added), `resolve.ts`, tests, ADR-0014, CHANGELOG.
- **How:** Test first: every removed term must resolve to nothing, the specific forms must still resolve, and re-seeding after dropping a term must delete it. Removing the terms was not enough: "band" still fuzzy-matched "rubber band". So trigram now refuses near-ties and lone words that only match part of a phrase.
- **Why:** A wrong guess costs a user more than a second question. Rejected a hand-kept stop-word list: it would drift from the catalog. The seed already deleted dropped terms for seeded items; the new test locks that in.
- **Learn:** Fuzzy matching undoes an exclusion list: delete a term from the dictionary and similarity search finds a near neighbour anyway, so ambiguity has to be handled where the match is made.

## Day 6: requests, state machine and expiry

- **What:** Migration 005; `modules/requests` (state machine, guarded persistence, service, router), `workers/requestExpiry.ts`, config, shutdown, ADR-0015.
- **How:** Test commit then code. The table test covers all 25 state × event pairs; Testcontainers Postgres and Redis cover the API, lazy expiry, the delayed job and the sweeper. To see the concurrency test mean something, I removed the `state` guard: it failed 3 runs of 3 within two rounds. CI also caught a wrong assumption in my first version of that test: it counted applied events, but a serial interleaving is legal, so it now asserts one move out of PINGING and an unbroken history.
- **Why:** The free tier sleeps and Redis forgets, so the database deadline is the truth, lazy expiry and a sweeper back it up, and the queue only makes expiry timely. Rejected a queue-only design and a separate worker service.
- **Learn:** Under READ COMMITTED a guarded UPDATE (`WHERE state = $from`) is safe because Postgres re-checks the row after waiting for the other writer; the loser gets zero rows and must reload, not retry blindly.

## Day 7a: fan-out, ping answers, price check

- **What:** Migration 006; `modules/requests` (`targets`, `pings`, `results`, `distanceBand`), `modules/shops/stockWrite`, `workers/pingFanout|pingDedupe|redis|index`, router, config, ADR-0016.
- **How:** Test commit then code. Pure functions first (targets, bands, merge and sort, dedupe with a fake Redis), then Testcontainers with real Postgres, Redis and BullMQ workers for the whole loop, the edge cases, and a Redis-stopped test. A red CI-style bug showed up in my own test setup twice (shops from earlier tests crowding the nearest 10), not in the code.
- **Why:** A yes teaches inventory even when it arrives after the request ended, so late answers are accepted (ADR-0016). Dedupe is one atomic Redis `SET NX EX`; if Redis is away we ping anyway, because a duplicate ping costs less than a failed request. Rejected checking then setting the key in two commands: two fan-outs could both pass.
- **Learn:** Take locks in one order everywhere (request row, then pings). Two code paths that lock the same two rows in opposite orders deadlock under load; one order makes them queue.

## Day 7b: the shop web app, and two fan-out fixes

- **What:** `apps/web` (Vite + React): login, onboarding, ping card, one dictionary file (hi/en), plain CSS, manifest and icons; `http/web.ts` (static files, SPA fallback, strict CSP); Dockerfile and CI build the web app; ADR-0017. Part A: fan-out backfill and a sweeper that re-queues a lost fan-out job (ADR-0016).
- **How:** Test commits first for both parts: a CSP/static-file test with a temp folder, then 70+ component, API-client and money tests with Testing Library and jsdom. Built the image and ran the real server to check the page, the headers and the whole ping flow with curl.
- **Why:** The API serves the app so there is one deploy and no CORS; rejected Cloudflare Pages for now. The token stays in localStorage (a shopkeeper's phone must stay logged in) and the CSP is the defence for the XSS risk; the trade-off is written down. Money is typed as rupees and converted to integer paise with integer arithmetic.
- **Learn:** `4.35 * 100` is `434.99999999999994` in floating point. Parse money as text, split on the dot and build integers; never multiply a decimal.

## Fix: a lost database connection must not crash Node

- **What:** `db/pool.ts` (`createPool`), `db/queryable.ts` (`withTransaction`), `server.ts`, `seedCatalogMain.ts`, `testing/startPostgres.ts`, two test files moved onto the shared helper, `db/pool.int.test.ts`, runbook, CHANGELOG.
- **How:** Test first: terminate an idle backend (and one held inside a transaction) and assert no uncaught exception, a warning with code 57P01 and no credentials, and a working next query. A plain Pool with no listener reproduced the CI failure 3 runs out of 3. The API process already had a pool listener since Day 3; the crash was in the test pools, which had none.
- **Why:** The Pool emits `'error'` when an idle client dies and Node throws an unhandled `'error'` event, so every pool must have a listener. The listener lives in one `createPool` so it cannot be forgotten. Tests also wait for Postgres to see every connection close before stopping the container, because `pool.end()` returns when clients are told to leave, not when they have left.
- **Learn:** An `error` event with no listener is an uncaught exception, not a log line. And a pg error object carries its whole client, password included: log `code` and `message`, never the error.
