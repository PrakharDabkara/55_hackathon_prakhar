## PR: limiter key diagnostic (known issue: per-IP bucket splits)

- **What:** traced every limiter on `POST /auth/otp/request`; added `LIMITER_DIAG` (`limiterDiag.ts`, wired through `ipLimit.ts`, the identity router, `app.ts`, config), a guard test that different phones share one IP budget, ADR-0058 known-issue update, runbook, changelog.
- **How:** read the route chain (api 300/min, IP request 10/10 min keyed only by `ipKey(req.ip)`, demo 403, per-phone in the database); the script's fake numbers stop at the 403, so the 429s are the IP bucket; tests first; the diagnostic logs a salted HMAC of the key, never the address.
- **Why:** the phone-in-the-key hypothesis is refuted by the code and a test, so no limiter change; `req.ip` varying fits 27 allowed requests but is unproven, so only evidence is added, and `trust proxy` stays at 1 (2 lets spoofing through).
- **Learn:** a counter that lets 27 through with a limit of 10 has at least three keys; count the keys before suspecting the counter.

## PR: desktop notice + phone-size windows

- **What:** a dismissible notice on both apps at 1024 px and wider, with buttons that open phone-sized windows (one, or buyer + shop side by side); `DesktopNotice.tsx/.css`, `lib/phoneWindows.ts`, `main.tsx`, e2e spec, changelog.
- **How:** checked the token keys first (`km-token` vs `km-seeker-token`: separate), so side-by-side is safe; the notice mounts in `main.tsx` beside each app, so no screen, route or API changed; `matchMedia` gates it; tests first; 360/412 screenshots compared byte for byte.
- **Why:** the shop app's brand rule overrides the given text, so the shop says "This app"; `window.open` without `noopener`, because `noopener` makes it return null and hides a blocked popup. Rejected: a CSS-only notice (cannot remember dismissal or open windows).
- **Learn:** `window.open` returns null both when blocked and when `noopener` is set, so the feature string decides whether you can detect a block.
